# ADR 0011: ログインは Google のみ・許可メールアドレス 1 件・JWT セッションで実装する

## Status

Accepted (2026-08-22)

## Context

本アプリはこれまでローカル（docker-compose + MySQL）でのみ動かしており、ログインが無くても実害が無かった。デプロイすると URL を知っている第三者に資産状況が見えてしまうため、公開前にログインが要る。

前提として、本アプリの利用者は**所有者 1 人だけ**である。複数人で使う予定は現時点で無く、Stock / Transaction などのデータもユーザーに紐付いていない（テーブルに userId が無い）。

`next-auth` と `@next-auth/prisma-adapter` は package.json に入っているが、実装ファイルは存在しなかった。

## 検討した代替案

- **案A（採用）：Google OAuth のみ・許可メールアドレスを環境変数で 1 件指定・JWT セッション**
  - ログイン成功後に `signIn` コールバックでメールアドレスを照合し、一致しなければ拒否する
  - ユーザーを DB に持たないため Prisma スキーマを変更しない
- **案B：PrismaAdapter で User / Account / Session / VerificationToken を持つ（DB セッション）**
  - NextAuth の標準構成で、マルチユーザー化するときはこれが要る
  - ただし利用者が 1 人に固定される現状では、User テーブルに保存する情報が実質メールアドレスだけになる。テーブル 4 つと `db:push` を足しても得るものが無い。不採用
- **案C：メール + パスワード（Credentials プロバイダ）**
  - パスワードのハッシュ化・強度チェック・リセット手段・総当たり対策を自前で持つことになる。所有者 1 人のために実装・保守する量が見合わない。不採用
- **案D：Basic 認証（middleware で固定の ID/パスワードを照合）**
  - 最小の実装で保護はできるが、資格情報が環境変数の平文で、ブラウザに保存されたまま失効させる手段が無い。不採用

## Decision

**Google OAuth のみを提供し、`ALLOWED_LOGIN_EMAIL` に一致するメールアドレスだけログインを許可する。セッションは JWT に閉じ、Prisma スキーマは変更しない。**

- 許可判定は `signIn` コールバックで行う。実装：[authOptions](../../src/lib/auth.ts)
  - `ALLOWED_LOGIN_EMAIL` が未設定なら**全員拒否**する。設定漏れが全開放にならないようにするため
  - Google 側で確認済み（`email_verified`）でないメールアドレスは、許可リストと一致しても拒否する
- 未認証アクセスの遮断は middleware で行う。実装：[middleware](../../src/middleware.ts)
  - 画面はログイン画面へリダイレクトし、遷移先を `callbackUrl` で引き継ぐ
  - `/api/*` は**リダイレクトせず 401 JSON** を返す。画面から fetch している API がログイン画面の HTML を受け取ると、呼び出し側で失敗を判別できないため
  - `/api/batch/*` は保護対象外。`X-API-Key` で認証しており、ブラウザのセッションを持たない cron から呼ばれる
- ログイン後の画面遷移は既存のヘッダーを流用し、ログイン中のメールアドレスとログアウト操作を右端に置く

### 理由

- 認証情報の管理（パスワード保管・再発行・二要素）を Google に委ねられる
- 許可リストが 1 件なら、ユーザー管理画面もユーザーテーブルも要らない
- JWT にすることで、本 ADR の作業を DB 移行（Issue #10）と切り離して完了できる

## 決定していないこと

- **マルチユーザー化したときの構成**。その時点で PrismaAdapter + DB セッションへ切り替える想定だが、データのユーザー紐付け（Stock / Transaction への userId 追加）をどう移行するかは決めていない
- **セッションの有効期限**。NextAuth の既定（30 日）のまま。単一ユーザー・自分の端末という前提で、短縮する根拠が現時点で無い
- **`/api/batch/*` の認証方式**。`X-API-Key` のまま据え置き。Vercel Cron 対応（`CRON_SECRET`）は Issue #10 の範囲
- **監査ログ**。誰がいつログインしたかは記録しない

## Consequences

- 環境変数に `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `ALLOWED_LOGIN_EMAIL` が必要になる。未設定だとログインできない（＝アプリが使えない）
- Google Cloud Console 側で、リダイレクト URI `{NEXTAUTH_URL}/api/auth/callback/google` の登録が要る。本番 URL が決まったら本番ぶんの URI を追加する
- サーバーコンポーネントから自アプリの `/api/*` を fetch している箇所（ダッシュボード・ポートフォリオ画面）は、セッション Cookie を引き継がないと 401 になる。[forwardSessionCookie](../../src/lib/server-fetch.ts) を経由すること。**新しくサーバー側 fetch を足すときも同様**
- JWT の署名に `NEXTAUTH_SECRET` を使う。変更すると既存のログイン状態がすべて無効になる

### プレモーテム（この決定が誤っていた場合）

- Google アカウントにログインできない状況（アカウント停止・二要素の端末紛失）になると、**本アプリにも入れなくなる**。復旧手段は Google アカウントの復旧のみで、アプリ側に迂回路が無い
- 家族など 2 人目に見せたくなった時点で、許可リストが 1 件という前提が崩れる。環境変数をカンマ区切りにする程度で足りるうちは案A の延長で済むが、データをユーザーごとに分ける必要が出たら案B への移行が要る
- `/api/*` を 401 で返すため、将来 API を外部ツール（スプレッドシート等）から叩きたくなったときにブラウザセッションでは通らない。API キー方式を別途足すことになる

## 見直しトリガー

- 所有者以外の利用者が増えたとき（許可リストが 2 件以上になったとき）
- データをユーザーごとに分ける要求が出たとき
- ブラウザ以外（外部ツール・スクリプト）から業務 API を叩きたくなったとき
- Google 以外のログイン手段が必要になったとき（アカウント復旧の迂回路が要るとき）
