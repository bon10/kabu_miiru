# ADR 0024: 株式分割・併合は取引とは別の記録として持ち、再生の途中で保有株数を換算する

## Status

Accepted (2026-11-15)

## Context

保有銘柄の SBIホールディングス（8473）が 2025-11-27 に 1 株 → 2 株の株式分割を行い、証券会社の口座では保有株数が 2 株 → 4 株、平均取得単価が半分になった。本アプリには分割を入力する手段が無く、保有株数と平均取得単価が証券会社の表示と食い違った。

本アプリの保有株数・平均取得単価は Transaction を再生して求める派生値であり（[ADR 0003](0003-transaction-as-source-of-truth.md)）、直接は書き換えられない。分割を反映するには、既存の買いの取引を「4 株・単価半分」に書き換えるしかなかった。この方法は買ったときの記録を失い、分割があった事実もどこにも残らない。

[ADR 0009](0009-portfolio-timeline-from-daily-close.md) は株式分割・併合の扱いを「決定していないこと」に置き、「株式分割・併合が発生し、過去終値と現在の保有株数が整合しなくなったとき」を見直しトリガーにしていた。今回の分割でこのトリガーが引かれた。

決めるにあたって、日次終値の原資料である Yahoo Finance chart API の挙動を実測した（2026-11-15。[external-apis.md](../external-apis.md)）。

- `indicators.quote[0].close` は、**過去の日のぶんも現在の株数の基準に換算済みの値**で返る。8473.T（2025-11-27 に 1→2）、7203.T（2021-09-29 に 1→5）、NVDA（2024-06-10 に 1→10）のいずれも、分割日の前後で終値が跳ばない
- `events=splits` を付けると、期間内の分割の日付と比率が返る

つまり、分割より後に取り込んだ日次終値はすでに分割後の基準になっている。一方、分割より前に日次の定期実行で保存した行は分割前の基準のまま残る（[saveDailyCloses](../../src/lib/daily-price.ts) は既存の行を上書きしない）。

## 検討した代替案

### 分割をどこに記録するか

- 案A（採用）：**取引とは別のテーブル `StockSplit` に持つ**。取引は約定時点の株数・単価のまま残し、再生の途中で分割日に保有株数へ比率を掛ける
- 案B：`TransactionType` に `SPLIT` を足す / 不採用の理由：Transaction の必須列（単価・金額・手数料）は分割では意味を持たず、ダミー値を入れることになる。取引の一覧・集計・件数など Transaction を読むすべての箇所で `SPLIT` を除外する分岐が要る。[ADR 0008](0008-initial-balance-transaction.md) も、種別を増やすと BUY / SELL で分岐している箇所すべてに波及することを理由に、初期残高で種別を増やさなかった
- 案C：分割日より前の取引を、分割後の株数・単価に一括で書き換える / 不採用の理由：買ったときの記録が失われ、取り消せない。書き換え済みかどうかを後から判別できず、二重に書き換える事故を防げない
- 案D：分割ぶんを「単価 0 の買い」として登録する / 不採用の理由：保有株数と平均取得単価は合うが、その日に買った事実は無い。初回購入日・購入時の指標（ADR 0021）・取引件数が実態とずれる

### どうやって入力するか

- 案A（採用）：**利用者が銘柄詳細画面で登録する。Yahoo が返す分割は「この内容で登録しますか」と候補として見せるだけにする**
- 案B：手入力だけ / 不採用の理由：分割に利用者が自分で気づく必要がある。今回も、気づいたのは分割の約 1 年後だった
- 案C：日次終値の定期実行で Yahoo の分割を見つけたら自動で登録する / 不採用の理由：Yahoo の分割の扱いは銘柄によって正しくない（1306.T の調整済み終値は分割が調整されていない。[external-apis.md](../external-apis.md)）。誤った分割が自動で入ると、保有株数が利用者の知らないうちに変わる

### 分割より前の日次終値をどうするか

- 案A（採用）：**分割を登録するときに、その銘柄の分割日より前の日次終値を Yahoo から取り直して置き換える。**保存する日次終値は常に「現在の株数の基準」とし、推移は分割日より前の日の保有株数を同じ基準に換算してから終値を掛ける
- 案B：日次終値は「その日の実際の株価」で持ち、Yahoo から取った値を分割の比率で割り戻す / 不採用の理由：どの行が分割の前に保存され、どの行が後に保存されたかを行ごとに判別する必要がある。日次終値を使う 200日線（ADR 0021 / 0023）は現在の基準で揃った系列を必要とするため、読み取りのたびに逆の換算も要る
- 案C：何もしない / 不採用の理由：分割前の基準の行と分割後の基準の行が混ざり、推移の評価額と 200日線が分割日で跳ぶ

## Decision

### 1. 分割は `StockSplit` に持つ

銘柄・分割日・分割前の株数・分割後の株数を 1 行で持つ（1 株 → 2 株の分割なら 1 と 2、5 株 → 1 株の併合なら 5 と 1）。同じ銘柄の同じ分割日は 1 行だけ（二重登録を防ぐ）。

保有株数・投資額の Source of Truth は、**Transaction と StockSplit の 2 つ**になる。ADR 0003 の「Stock 側のフィールドは派生値で、変更のたびに再計算する」という考え方は変えず、再計算の入力に分割を足す。

### 2. 再生では、分割日に保有株数だけを換算する

[replayTransactions](../../src/lib/stock-aggregation.ts) は、取引を並べて再生する途中で、分割日に保有株数へ「分割後の株数 ÷ 分割前の株数」を掛ける。**取得原価は動かさない。**分割で株主が払った金額は変わらないため。結果として平均取得単価が比率ぶん変わる。

分割日当日の取引は、分割を先に適用してから処理する。分割日は権利落ち日（株価が分割後の水準に変わる最初の営業日）であり、その日の取引は分割後の株数・単価で約定しているため。

再生に関わる処理（銘柄集計の再計算・推移の再構成・初期残高の生成）はすべて分割を入力に取る。

### 3. 日次終値は「現在の株数の基準」に揃える

- 分割を登録するとき、その銘柄の分割日より前の日次終値を Yahoo から取り直して置き換える（[replaceDailyClosesBefore](../../src/lib/daily-price.ts)）。取り直せなかったときは**分割の登録ごと差し戻す**。保有株数だけ換算して終値が古いままだと、推移の評価額が比率ぶんずれたまま気づけないため
- 推移（[computeTimeline](../../src/lib/portfolio-timeline.ts)）は、評価額を `その日の保有株数 × その日より後の分割の比率 × 終値` で出す。投資元本と実現損益は、その日の実際の株数・単価で計算したまま

### 4. Yahoo の分割は候補として見せるだけにする

銘柄詳細画面は、最初の取引より後で、まだ登録していない分割を Yahoo から取って表示する。登録するかどうかは利用者が決める。最初の取引の日以前の分割は候補にしない（取引がすでに分割後の株数で記録されているため）。

### 5. 分割の削除は、取引履歴の編集・削除と同じ設定で許可する

保有株数と平均取得単価を書き換える操作なので、取引の削除と同じ扱いにする（既定は無効）。登録は取引の登録と同じく常に許可する。

## 決定していないこと

- **端数の処理**。併合や 1 → 1.5 の分割では 1 株に満たない端数が出て、実際には現金で払い戻される。本 ADR は比率を掛けた株数をそのまま保有株数にする。端数の払い戻しは売却として別に登録する想定だが、入力の補助は作らない
- **分割日より前の受取配当**。`DividendHistory.shares` は配当明細の数量を写した値（ADR 0015）で、分割で換算しない。1 株あたりの配当を期をまたいで比べる機能は無いため、今は影響しない
- **目標価格（`Stock.targetPrice`）と 1 株配当金（`Stock.dividendPerShare`）**。どちらも 1 株あたりの値だが、分割の登録では書き換えない。利用者が入力した値を、利用者に見せずに変えないため
- **基準チェックの指標への影響**。FCF利回りと Altman Z は `現在値 × 株式数` を使う（ADR 0023）。分割の直後、Yahoo の通期決算の株式数が分割前のままかどうかは確認していない
- **10 年より前から保存している日次終値**。chart API で日次の値を 10 年より長く取る手段を確認できていないため、分割の登録で置き換えるのは直近 10 年ぶんまで
- **Yahoo の分割情報と登録済みの分割が食い違うときの通知**

## Consequences

- スキーマに `StockSplit` を追加する（マイグレーション `4_add_stock_split`。表を足すだけ）
- API：`GET / POST /api/stocks/{id}/splits`、`DELETE /api/stocks/{id}/splits/{splitId}`、`GET /api/stocks/{id}/splits/candidates`
- 銘柄詳細画面に次の 3 つを追加する
  - 画面上部の操作ボタンの列に「株式分割」ボタン。押すと手入力の登録ダイアログが開く（購入・売却・受取配当の登録と同じ場所に置く）
  - Yahoo の候補の帯。未登録の分割があるときだけ、操作ボタンの列のすぐ下に出す（画面の下のほうに置くと、候補が出ていても気づけないため）
  - 「株式分割・併合」のカード。登録済みの分割の一覧と削除。1 件以上あるときだけ、取引履歴の下に出す
- **分割日より前の取引を、すでに分割後の株数に書き換えてある銘柄では、分割を登録すると二重に換算される。**登録の前に取引を元の株数・単価へ戻す必要がある（画面に注意書きを出す）。SBIホールディングス（8473）がこれに当たる
- `saveDailyCloses` の「既存の行は上書きしない」という規則に、分割の登録という例外ができる
- 分割の登録は Yahoo への問い合わせを伴うため、Yahoo が応答しないあいだは登録できない（その銘柄に分割日より前の日次終値が 1 件も無ければ問い合わせない）

### プレモーテム（この決定が誤っていた場合）

- **Yahoo の終値が分割で換算されていない銘柄があった場合**：その銘柄では、分割日より前の評価額が比率ぶん大きく（併合なら小さく）出る。保有株数・平均取得単価・投資元本は Yahoo に依存しないため正しいまま。影響は推移グラフと 200日線に限られ、原資料（取引と分割）は残っているので、終値の持ち方を変えれば作り直せる
- **誤った分割を登録した場合**：分割を削除すれば、保有株数と平均取得単価は元に戻る。日次終値は Yahoo の現在の値に置き換えただけなので、戻す必要が無い

## 見直しトリガー

- Yahoo の日次終値が分割で換算されていない保有銘柄が見つかったとき（推移の評価額が分割日で跳ぶ）
- 端数の払い戻しを伴う分割・併合が保有銘柄で起きたとき
- 分割に気づくのが遅れて実害が出たとき（→ 定期実行での検出と通知を検討する）
- 証券会社の取引履歴の取り込みを始めるとき（証券会社側が分割をどう出力するかに合わせる）
- 日次終値の取得元を Yahoo Finance 以外に変えるとき（過去の終値が分割で換算済みかどうかは取得元ごとに違う）
