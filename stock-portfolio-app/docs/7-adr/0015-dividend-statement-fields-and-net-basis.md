# ADR 0015: 受取配当は証券会社の配当明細（数量・配当合計・税額合計・受取金額）を写して保存し、集計は手取り基準とする

## Status

Accepted (2026-09-03)

## Context

受取配当（`DividendHistory`）はこれまで税引前の総額 `dividendAmount` だけを保存していた（ADR 0007）。しかし証券会社の口座に実際に入るのは税金を引いた後の金額で、本アプリはその差額をどこにも記録していない。ユーザーの配当明細では次のようになっている：

| 商品 | 銘柄 | 単価 | 数量 | 配当・分配金合計（税引前） | 税額合計 | 受取金額 |
|---|---|---|---|---|---|---|
| 国内株式 | フルテック 6546 | 10 | 100 | 1,000 | 203 | 797 |
| 米国株式 | JPM NQ EPI ETF (JEPQ) | 0.70497 | 5 | 3.52 | - | 2.55 |
| 米国株式 | TAIWAN SEMI ADR (TSM) | 0.93933 | 1 | 0.94 | - | 0.60 |

現行実装が記録しているのは「配当・分配金合計」の列だけで、ダッシュボードの YTD 配当も年計・半期も推移グラフの累計配当も、すべて税引前で積み上がっている。実感（口座に入った額）と数字が合わない。

同時に、その配当合計の**作り方**にも問題がある。ADR 0007 は `1 株あたり配当金 × 登録時点の Stock.sharesHeld` で総額を確定すると決めたが、**配当額は権利確定日の株数で決まる**のに対し、`Stock.sharesHeld` は権利確定後の売買まで織り込んだ別の数字である。両者は入金までの数ヶ月のあいだに簡単にずれる。

| 権利確定後にやったこと | 登録時点の `sharesHeld` | 保存される配当合計 | 気づけるか |
|---|---|---|---|
| 100 株 買い増した | 200 | 2,000 円 | **気づけない（黙って 2 倍）** |
| 50 株 売った | 50 | 500 円 | **気づけない（黙って半分）** |
| 全部売った | 0 | 登録できない（NO_SHARES） | 気づける |

正しいのはいずれも明細どおりの 1,000 円である。上の 2 行はエラーも警告も出ないまま誤った金額が年計・グラフに乗る。ADR 0007 のプレモーテムはこの危険を予見していたが、当時は受け入れる判断をしていた。

そもそも証券会社は配当額を掛け算で出していない。権利確定日の株主と株数は株主名簿で確定しており、そこから決まった金額が明細に届く。明細の数量は「計算に使う値」ではなく**確定した事実の記録**である（名簿の仕組みについては一般的な理解で、特定の証券会社の実装を確認したものではない）。本アプリだけが掛け算をやり直しているため、掛ける株数を取り違えると答えが狂う。

ここで問題になるのが**米国株式の行**である。**税額合計の列が「-」なのに受取金額は減っている**（JEPQ は 3.52 → 2.55、TSM は 0.94 → 0.60）。減り方も国内株の 203/1,000 とは違い、銘柄ごとにも違う。つまり **「税額」を入力項目にすると米国株では税金を記録できない**。一覧の税額合計欄から読めない控除が存在する。

## 検討した代替案

- **案A（採用）：明細の 4 項目（数量 / 配当・分配金合計 / 税額合計 / 受取金額）を `DividendHistory` に持ち、数量はユーザーが明細から入力し、集計は受取金額（手取り）で行う。** 既存レコードは移行せず、追加列を NULL のまま残す。
- **案B：現状維持（税引前で通す）。** スキーマ変更が要らず、配当利回り（BR-201）が税引前基準であることとも整合する。/ 不採用：口座に入った額を一切記録できず、ユーザーの要望に応えられない。
- **案C：スキーマは変えず、ユーザーが 1 株あたり配当金の欄に「受取金額 ÷ 数量」を入力する運用にする。** 変更ゼロで手取りを記録できる。/ 不採用：割り切れないと端数が落ちて数円ずれる（797 円・133 株なら 5.99 × 133 = 796.67）うえ、税引前がどこにも残らず、保存値の意味が運用の口約束になる。
- **案D：税率（20.315% 等）を定数で持ち、集計時に税引前へ掛けて手取りを出す。** スキーマ変更不要。/ 不採用：上記のとおり米国株は控除率が銘柄ごとに違い、非課税口座も表現できない。実額と一致しない。
- **案E：税額合計だけを列として追加し、受取金額は「配当合計 − 税額」で導出する。** 列が 1 本で済む。/ 不採用：米国株は明細の税額合計が空欄なので、入力できるものが無くなる。
- **案F：数量は現在の保有株数のまま（ADR 0007 を維持）で、税額・受取金額の列だけ足す。** 入力が 1 項目減る。/ 不採用：上表の「黙って 2 倍」が残る。税金を正しく記録できても、その土台の配当合計が狂っていては意味がない。
- **案G：数量の初期値に現在の保有株数を入れ、違うときだけ直してもらう。** 大半のケースで入力を省ける。/ 不採用：**数字が埋まっていると「正しそうに見えて」確認されない**。ずれているときこそ直してほしいのに、そのときだけ気づけない。手入力にした意味が薄れる。

## Decision

受取配当は**証券会社の配当明細 1 行をそのまま写し取る**。`DividendHistory` に次の 3 列を NULL 可で追加する：

| 列 | 明細の列 | 内容 |
|---|---|---|
| `shares` `Decimal(15,4)` | 数量 | 配当計算の対象株数。**ユーザーが明細から入力**する（`Stock.sharesHeld` は使わない） |
| `dividendAmount`（既存） | 配当・分配金合計 | 税引前。`1 株あたり配当金 × 数量` で確定（BR-202） |
| `taxAmount` `Decimal(15,2)` | 税額合計 | 明細が「-」なら未入力でよい |
| `netAmount` `Decimal(15,2)` | 受取金額 | 手取り。**集計の基準** |

- **入力は明細の写し**：単価（1 株あたり配当金）と数量を入れると配当合計が決まり、**税額合計と受取金額はどちらか片方**を入れれば残りが `配当合計 − 入力値` で埋まる。国内株は税額合計から、米国株は受取金額から入力することになる。
- **両方入力されたときは引き算せずそのまま採り、合計との一致は検証しない**。米国株は「税額合計 + 受取金額 ≠ 配当合計」になりうるため。
- **両方未入力なら `taxAmount` / `netAmount` は NULL**（税額不明）として保存する。
- **掛ける数量は明細の数量**とし、ユーザーが入力する（**ADR 0007 からの変更**）。`Stock.sharesHeld` は参照しない。未入力を保有株数で補うこともしない（補うと上表の取り違えが復活するため、`NO_SHARES` で弾く）。
- **入力フォームの数量欄は空欄から始める。** 現在の保有株数を初期値に入れない。ずれているときほど「埋まっていて正しそうに見える」状態が危険なため、毎回明細を見て入力する形にする（案G を不採用にした理由）。
- 数量を明細から取ることで、**権利確定後に売り切った銘柄の配当も記録できる**（ADR 0007 の「保有株数 0 の銘柄は登録不可」は「数量 0 では登録不可」に変わる）。
- **`DividendHistory.shares` は Transaction から導出しない独立の事実**として扱う。ADR 0003 が「Transaction を Source of Truth とし、`Stock` 側は再計算される射影」と定めているのは**保有株数・投資額**であって、配当明細の数量はその射影ではない。証券会社から届いた確定値なので、**Transaction を直しても再計算しない**（`recalculateStockAggregates` の対象外）。`dividendAmount` が登録時点で凍結されるのと同じ扱い（ADR 0007）。
- **集計は手取り基準**。`netAmount` を使い、**NULL のときだけ `dividendAmount`（税引前）で代用**する。対象は YTD 配当・年計・半期・銘柄別・推移グラフの累計配当。
- 金額は従来どおり**受取通貨建てのまま**保持し、円換算は読み取り時に当日レートで行う（ADR 0006）。
- 計算・検証は純粋関数 [resolveDividendTax / netDividendAmount](../../src/lib/dividend.ts) に集約し、API とフォームで共用する（単体テストあり）。

### 理由

- 明細の 4 列をそのまま持つので、ユーザーは**見たまま転記するだけ**で計算しなくてよい
- 数量を明細から取ることで、**権利確定日の株数と登録時点の保有株数のずれ**（上表）が構造的に消える
- 受取金額を実額で持つため、米国株の「税額合計が空欄」でも税金を記録できる（`配当合計 − 受取金額` が現地源泉徴収税を含む控除額になる）
- **口座区分（NISA / 特定 / 一般）をモデリングしなくてよい**。非課税なら受取金額 = 配当合計になるだけで、実額が自然に表現される
- 税引前を捨てずに残すため、配当利回り（BR-201、税引前基準）との整合も保てる

## 決定していないこと

- **既存レコードは移行しない。** 追加列は NULL のままで、集計では税引前が手取りとして代用される。つまり**集計対象に新旧が混ざる**。過去分を正したければ入力し直す。
- **税額の内訳**（国内税 / 現地源泉徴収税）は分けて持たない。`配当合計 − 受取金額` の 1 本にまとめる。外国税額控除の計算には足りない。
- **`Stock.dividendAmount`（予想年間配当、マスタ由来）は税引前のまま**。実績（手取り）と基準が違うので、並べて表示する箇所ではラベルで区別する。
- **入金日レートでの確定換算**は行わない（ADR 0006 の決定を維持）。

## Consequences

- スキーマ：`DividendHistory` に `shares` / `taxAmount` / `netAmount` を追加（すべて NULL 可）。既存レコードは無変更。**ローカルと本番（TiDB Cloud、ADR 0013）の双方に反映が要る。** NULL 可の列追加なので既存行を壊さず、移送スクリプト [migrate-to-remote-db.js](../../scripts/migrate-to-remote-db.js) は行をそのまま複写するため変更不要。
- API：`POST /api/dividends` が `shares` / `taxAmount` / `netAmount` を受け取る。`GET /api/dividends` は 4 項目と `netAmountJpy` を返す。`GET /api/dividends/summary` は `yearTotal` を手取り基準にし、内訳として `yearGrossTotal` / `yearTaxTotal` を追加で返す。
- 集計：`/api/summary` の `ytdDividendReceived`、`/api/portfolio/timeline` の `cumulativeDividends` が手取り基準になる。**同じ配当データでも本 ADR 適用後に登録した分だけ数字が下がる**。
- UI：受取配当フォームが明細と同じ並び（単価・数量・税額合計・受取金額）になり、配当合計と埋まった側の値をその場で表示する。**数量欄は空欄始まりで必須**。一覧・銘柄詳細は手取りを主に出し、税引前と税額を副次表示する。
- `DividendStockOption`（フォームに渡す銘柄候補）から `sharesHeld` を落とした。フォームが保有株数を知る必要がなくなったため。
- 入力欄の刻みを `step="0.01"` から `step="any"` に変えた。明細の単価は小数第5位まで出ることがある（JEPQ 0.70497）ため。
- ビジネスルールは [BR-202](../2-domain/business-rules.md)、用語は [ユビキタス言語](../2-domain/ubiquitous-language.md)。

### プレモーテム（この決定が誤っていた場合）

- 既存レコードを移行しないため、**年計・推移グラフで税引前と手取りが混ざった数字**が出続ける。過去分を入力し直すまで、前年比の比較は基準が揃わない。
- 税額を 1 本にまとめたため、国内税と現地源泉徴収税を分けたい要求（外国税額控除の試算など）が出たら、また列を足すことになる。
- 数量を毎回手入力にしたため、**打ち間違いがそのまま配当合計になる**。初期値を置かないぶん既定値ミスは消えたが、代わりに入力負荷と打鍵ミスを引き受けた。件数が増えて負担になれば、初期値ありへ戻す圧力がかかる。
- ADR 0007 が「クライアントの株数を使わない（改ざん・陳腐化を避ける）」とした耐性は、**単一ユーザー運用（ADR 0011）を前提に手放した**。所有者しかログインできないので改ざんの動機が無く、陳腐化はむしろ `Stock.sharesHeld` を使う側に起きる、という読みに立っている。この前提が崩れれば判断ごと崩れる。

## 見直しトリガー

- **外国税額控除の試算**をしたくなったとき → 税額を国内税 / 現地源泉徴収税に分けて持つ案を検討する
- **口座区分（NISA / 特定 / 一般）そのものを集計軸にしたい**要求が出たとき → 実額だけでは非課税枠の管理ができないため、口座区分を持つ案を検討する
- **旧レコードを一括で手取りへ移行したい**要求が出たとき → 税率を仮定した移行スクリプトを書くか、入力し直すかを決める
- **数量の毎回入力が負担になったとき** → 初期値ありへ戻す案（案G）を、確認を促す UI（明細と違う可能性の警告など）とセットで再検討する
- **所有者以外が使い始めたとき（ADR 0011 の単一ユーザー前提が崩れたとき）** → クライアントが送る数量をそのまま信じる判断を再検討する。ADR 0011 の「許可リストが 2 件以上になったとき」トリガーと連動する
- **権利確定日を記録したい**要求が出たとき → 数量とあわせて権利確定日を持ち、保有株数から数量を復元できるようにする案を検討する
- ADR 0006 が「入金日レートで確定換算」へ動くとき → 受取金額を入金日の円貨額で持つ案と整合を取り直す
