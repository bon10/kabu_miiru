# ADR 0007: 移行データの保有は「初期残高 Transaction」で表す

## Status

Accepted (2026-08-14)

## Context

[ADR 0003](0003-transaction-as-source-of-truth.md) は保有株数・投資額の Source of Truth を `Transaction` と定めたが、実データはこの前提を満たしていない。2026-08-14 時点の実測値：

| 項目 | 件数 |
| --- | --- |
| 銘柄（`Stock`） | 67（うち保有 55） |
| 売買取引（`Transaction`） | 3 |
| 購入日（`purchaseDate`）が入っている銘柄 | 7 |
| 米国株 | 28 |

保有 55 銘柄のうち 48 銘柄が、2025-09-10 の TSV 一括インポート由来で**購入日も取引履歴も持たない**（`Stock.createdAt` が全件 2025-09-10）。[import/tsv](../../src/app/api/import/tsv/route.ts) が `Stock` に直接書き込み、`Transaction` を生成しないためである。

これにより ADR 0003 の見直しトリガー「Transaction を持たない保有が集計の前提を崩していることが確認されたとき」が発火した。実害は次の 2 点：

- ポートフォリオ推移 API が `Transaction` のみから再生するため、**48 銘柄が推移グラフに一切載らない**
- 任意の過去時点の保有株数を引けないため、評価額の推移（[ADR 0008](0008-portfolio-timeline-from-daily-close.md)）が計算できない

## 検討した代替案

- **案A（採用）**：購入日がある銘柄はその日、無い銘柄は TSV 取り込み日 2025-09-10 を**起点日**として初期残高 Transaction を生成する
- **案B**：判明している最古の購入日 2025-02-16 に全銘柄を揃える / **不採用**：「2025-02 から 48 銘柄を保有していた」は事実ではない。過去の資産額を実際より大きく描くことになり、グラフが虚偽になる
- **案C**：48 銘柄ぶんの購入日を証券会社の履歴から手入力する / **不採用**：最も正確だが 48 件の手作業を要する。案A でも起点日以降は正しく動き、購入日が判明した銘柄から個別に直せる（Decision 末尾の可変性を参照）ため、先に案A で動かしてから必要に応じて埋める
- **案D**：`Stock.sharesHeld` を起点株数とみなし Transaction を作らない / **不採用**：保有株数の Source of Truth が `Transaction` と `Stock` に二重化し、ADR 0003 を実質的に破棄することになる

## Decision

移行データ由来の保有を **初期残高 Transaction** として表現する。

### 識別方法

`TransactionType` は `BUY` / `SELL` のまま変更せず、`Transaction.isInitialBalance`（Boolean、既定 `false`）を追加して初期残高を識別する。集計上は BUY と完全に同一に扱う。

理由：計算上は BUY と等価であり、区別したいのは「**取引日が実データか推定値か**」だけである。`TransactionType` に値を増やすと BUY/SELL を分岐している 10 ファイル・30 箇所に波及するのに対し、フラグなら既存の分岐に触れずに出自だけを記録できる。

### 起点日

- `purchaseDate` が入っている 7 銘柄 → **その日付**
- 購入日を持たない 48 銘柄 → **2025-09-10**（`Stock.createdAt` ＝ TSV 一括インポート日）

理由：2025-09-10 にその株数を保有していたことは事実である。それ以前に保有していたかは不明であり、推定で埋めない。「事実として言えるところまで」を起点にする。

### 株数・単価

`Stock.sharesHeld` と `Stock.avgAcquisitionPrice` をそのまま初期残高 Transaction の株数・単価とする。手数料は 0。米国株の単価はドル建てのまま保存する（[ADR 0005](0005-us-stock-jpy-conversion.md)）。

### 起点日は後から変更できる

[recalculateStockAggregates](../../src/lib/stock-aggregation.ts) が `Transaction` から毎回全再計算する構造のため、購入日が判明した銘柄は初期残高 Transaction の日付を書き換えれば、保有株数・平均取得単価・実現損益・推移グラフのすべてが自動で追従する。この可変性は案A を選べる前提であり、失ってはならない性質である。

## 決定していないこと

- **起点日より前の期間をグラフでどう見せるか**（非表示 / 破線 / 注記）は ADR 0008 側の未決事項として扱う
- **48 銘柄の購入日を今後埋めていく運用にするか**。埋めなくても動作するため、必要が生じてから決める
- **初期残高 Transaction をユーザーが UI から編集できるようにするか**。現状の編集は `allowTransactionEdit` 設定（既定オフ）の配下にある
- **`isInitialBalance` を集計ロジックで参照するか**。現時点では出自の記録のみに使い、計算は一切分岐させない

## Consequences

- **スキーマ**：`Transaction.isInitialBalance Boolean @default(false)` を追加する
- **移行**：既存 55 保有に対し初期残高 Transaction を生成するスクリプトが必要。実行後に全銘柄で `recalculateStockAggregates` を回し、`sharesHeld`・`avgAcquisitionPrice` が移行前の値と一致することを検証する（一致しなければ移行が誤っている）
- **TSV インポート**：今後のインポートも `Stock` 直書きではなく初期残高 Transaction を生成する経路に変える。ここを直さないと同じ乖離が再発する
- **既知の不具合を先に塞ぐ必要がある**：[recalculateStockAggregates](../../src/lib/stock-aggregation.ts) は `if (shares <= 0) continue` により、保有ゼロ時点の SELL を**警告なく読み飛ばす**。起点日を既存の SELL より後ろにずらすと、その売却の実現損益が黙って消える。`validateSellTransaction` は現在の合計株数しか見ておらず日付順序を検証しないため、日付編集を許すなら順序バリデーションを追加する
- **推移グラフ**：48 銘柄が推移の対象に入り、ADR 0008 の評価額推移が計算可能になる

### プレモーテム（この決定が誤っていた場合）

起点日 2025-09-10 が実態とかけ離れていた場合、グラフの左端が実際の投資開始より後ろにずれ、「いつから増えたか」が過小に見える。ただし**資産額そのものは誤らない**（起点日以降はすべて実データ）。影響は「見える期間が短い」ことに留まり、購入日を個別に直せば解消する。

対して案B を採っていた場合、資産額の推移そのものが虚偽になる。しかもグラフは自然に見えるため誤りに気付きにくく、訂正も困難である。誤ったときの回復可能性で案A が優る。

## 見直しトリガー

- 48 銘柄の購入日が証券会社の履歴等から一括で取得できるようになったとき
- 起点日（2025-09-10）より前の推移を見たい要求が出たとき
- 初期残高 Transaction と実際の売買 Transaction を**集計上で**区別する必要が生じたとき（現状はフラグを持つだけで計算は同一）
- TSV インポート経路の修正漏れ等で、Transaction を持たない保有が再び発生したとき
