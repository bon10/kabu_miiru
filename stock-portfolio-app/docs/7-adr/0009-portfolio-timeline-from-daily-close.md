# ADR 0009: ポートフォリオ推移は日次終値から読み取り時に再構成する

## Status

Accepted (2026-08-14)

## Context

現行の [/api/portfolio/timeline](../../src/app/api/portfolio/timeline/route.ts) は `Transaction` と `DividendHistory` だけから月末スナップショットを再生し、次の 3 本を返している。

- `investedAmount`（取得原価）
- `cumulativeRealizedPL`（累計実現損益）
- `cumulativeDividends`（累計配当受取）

**時価が 1 本も含まれていない。** 取得原価は買わない限り動かないため、線が動くのは売買か配当を入力した月だけになり、株価変動によるポートフォリオの増減が見えない。一般的な投資アプリが示す「資産評価額の推移」になっていない。

評価額の推移を出すには、任意の過去日について「**その日の保有株数 × その日の終値 × その日のレート**」が要る。しかし現状のデータは以下のとおりで、過去を描く材料が無い。

| テーブル | 件数 | 最古 |
| --- | --- | --- |
| `PriceHistory` | 185 | 2026-03-26 |
| `ExchangeRate` | 16 | 2026-07-03 |

加えて `PriceHistory.recordedAt` は任意時刻であり、場中に取得した値と終値が混在している。日次の時系列としては使えない。

なお、任意時点の保有株数を引ける前提は [ADR 0008](0008-initial-balance-transaction.md) が担う。

## 検討した代替案

- **案A（採用）**：銘柄ごとの日次終値と日次 USD/JPY を保存し、評価額は読み取り時に「株数 × 終値 × レート」で算出する
- **案B**：ポートフォリオの合計評価額を日次スナップショットとして保存する / **不採用**：理由は 3 点
  1. **その日にアプリが動いていないと永久に欠測になる。** 本アプリは常時稼働しない（ローカルの docker-compose 運用）
  2. 過去の取引や起点日を修正しても古い数字が残り、「Transaction が Source of Truth」（ADR 0003）と衝突する
  3. 合計値しか残らないため、銘柄別の推移を後から出せない
- **案C**：案A を原資料とし、案B を再生成可能なキャッシュとして併用 / **不採用**：55 銘柄・数年規模では読み取り時計算で足りる。原資料が残っていればキャッシュは後からいつでも足せるため、今決める必要がない（決定の YAGNI）

## Decision

### 保存するのは原資料のみ

**銘柄ごとの日次終値**と**日次 USD/JPY レート**だけを保存する。ポートフォリオの評価額・損益は保存せず、読み取り時に算出する。

### 欠測は後追いで埋められる

Yahoo Finance の chart API は `?range=…&interval=1d` で期間分の日次終値を **1 リクエストで**返す。

> 2026-08-14 に `https://query1.finance.yahoo.com/v8/finance/chart/7203.T?range=1mo&interval=1d` を実行し、1 レスポンスに 22 営業日分の終値が含まれることを実測で確認した。Yahoo Finance は非公式 API で公式ドキュメントが存在しないため、この挙動は実測に基づく記述であり、仕様として保証されたものではない。

したがって 1 ヶ月アプリを止めていても、55 銘柄 × 1 リクエストで穴を埋められる。**1 日ぶんの更新とリクエスト数は変わらない**。これが案A を成立させている性質であり、案B には無い。

### 円換算は各時点のレートで統一する

ある日の評価額と取得原価は、**どちらもその日の USD/JPY** で換算する。ADR 0005 の「取得も評価も同一レートで換算する（＝為替損益を損益に含めない）」原則を、当日から各過去日へ拡張したものである。最新時点では ADR 0005 の当日レート換算と一致する。

過去日にも当日レートを適用すると、今日のドル円が動くだけで過去の資産曲線が全体的に上下してしまうため、これを避ける。

### 欠測日は前営業日で埋める（forward-fill）

土日祝・取得失敗日は直前の営業日の終値で埋める。日本市場と米国市場で営業日が異なるため、合計を出すには必須となる。

### 起点日より前は描かない

初期残高の起点日（ADR 0008、購入日不明の銘柄は 2025-09-10）より前は保有状況が不明なため、グラフの対象外とする。ゼロで描くと起点日に資産が突然発生したグラフになり、実態を誤って伝える。

## 決定していないこと

- **欠測を埋めるトリガーの自動化**。現状は [/api/batch/daily-close](../../src/app/api/batch/daily-close/route.ts) を明示的に叩く手動運用。cron やアプリ起動時の自動補完を入れるかは、実際の運用頻度を見てから決める
- **グラフに出す指標**。現状は「評価額・投資元本・評価損益・累計配当」。買い増しの影響を除いた時間加重収益率（TWR）まで出すかは未定
- **株式分割・併合の扱い**（調整済み終値を使う / 分割イベントを取り込む / 手動対応）
- **グラフの粒度**（現状は日次のみ。週次・月次の切り替えを持つかは未定）
- **表示期間の追加**（四半期・年初来など。現状は今月・先月・1年・3年・5年・全期間の 6 種）
- **日次終値の保持期間**。銘柄数 × 日数で増え続けるが、55 銘柄 2 年で約 27,000 行のため当面は放置する

### 実装で確定した事項（2026-08-14）

- **日次終値の保存先**：既存 `PriceHistory` の拡張ではなく **新テーブル `DailyPrice`**（`(stockId, priceDate)` ユニーク）。`PriceHistory` は `recordedAt` が任意時刻で場中の値と終値が混在しており、時系列の再構成に使えないため分離した
- **初回バックフィルの期間**：`range=2y` で実行。55 銘柄・27,202 件の終値と 503 件の USD/JPY を約 14 秒で取得した
- **助走期間**：起点日が休場日（土日祝）だと直前営業日の終値を引き継げないため、起点日の 14 日前から forward-fill の状態だけを作る

### 表示期間の指定（Issue #9、2026-08-16）

期間は `range` プリセット（`thisMonth` / `lastMonth` / `1y` / `3y` / `5y` / `all`）で指定する。**期間の解決はクライアントではなくサーバー側で行う**（クライアントは選択肢の名前だけを送る）。閲覧者の端末のタイムゾーンで「今日」が変わってはならないため。実装：[timeline-range.ts](../../src/lib/timeline-range.ts)

> **補足（2026-08-26 / ADR 0012）**：本 ADR は当初「『今日』の判定はサーバーのローカル暦日に依存する」と書いていたが、[ADR 0012](0012-date-key-in-jst.md) でこの依存を解消した。暦日は実行環境のタイムゾーンによらず JST で判定する。サーバー側で解決するという結論自体は変わらない。

累計値（実現損益・配当）は期間を絞っても起点日からの積み上げを維持する。表示範囲は「どの日を点として返すか」だけを決め、計算自体は常に起点日から回す。

## Consequences

- 日次終値と日次 USD/JPY を保存する領域と、**期間指定で取得するバックフィル処理**が必要になる
- [getCurrentUsdJpyRate](../../src/lib/exchange-rate.ts) は「当日 1 件を取りに行く」実装であり、過去日を範囲で取り込む経路を追加する
- [/api/portfolio/timeline](../../src/app/api/portfolio/timeline/route.ts) は返す指標が変わる（投資額・実現損益・配当 → 評価額・投資元本・評価損益ほか）。粒度も月末固定から日次ベースに変わり、[portfolio-timeline-chart](../../src/components/portfolio/portfolio-timeline-chart.tsx) も追随する
- [fetchMultipleStockPrices](../../src/lib/stock-price.ts) は 55 銘柄を**直列**で回している。バックフィルもこの経路を使うため、画面リクエストからではなくバッチ経路で実行する前提とする
- ADR 0008 の初期残高 Transaction が前提。これが無いと 48 銘柄の過去株数を引けず、評価額が算出できない
- 取得失敗が続くと forward-fill が長く伸び、実勢とずれる。欠測が何日続いたかを記録し、UI で判別できるようにする

### プレモーテム（この決定が誤っていた場合）

読み取り時計算が遅くなった場合は、日次スナップショットのキャッシュ（案C）を後から追加できる。原資料の終値が残っているためキャッシュは再生成可能で、本決定の**取り消しではなく追加**で対処できる。

対して案B を採っていた場合、アプリを止めていた期間の欠測と、過去修正の反映が**不可逆に失われる**。後から案A に切り替えても、失った期間のデータは取り戻せない。回復可能性の非対称性が案A を選ぶ最大の理由である。

## 見直しトリガー

- 読み取り時の再構成が表示 UX を損なう規模になったとき（案C のキャッシュ併用を検討）
- 為替損益を損益として明示したい要求が出たとき（ADR 0005 と共通のトリガー）
- 株式分割・併合が発生し、過去終値と現在の保有株数が整合しなくなったとき
- Yahoo Finance の chart API が `range` / `interval` を受け付けなくなったとき（非公式 API のため仕様変更リスクを負っている）
- USD 以外の外貨建て銘柄を扱うとき（ADR 0005 と共通）
