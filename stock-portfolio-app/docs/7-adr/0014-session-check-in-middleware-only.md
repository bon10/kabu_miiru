# ADR 0014: ログイン済みかどうかの判定は middleware だけが行う

## Status

Accepted (2026-08-26)

## Context

2026-08-26、本番（Vercel + カスタムドメイン）でログイン直後に `ERR_TOO_MANY_REDIRECTS` が発生した。ローカルでは再現せず、**原因を特定できないまま解消した**。

当時、「ログイン済みか」を 2 か所が別々の方法で判定していた。

| 場所 | 使っていた関数 | 実行環境 | 目的 |
| --- | --- | --- | --- |
| `src/middleware.ts` | `getToken`（`next-auth/jwt`） | Edge | 未認証アクセスの遮断（ADR 0011） |
| `src/app/login/page.tsx` | `getServerSession` | Node | ログイン済みなら `/` へ戻す（利便性） |

両者の判定が食い違うと、middleware が `/login` へ送り、`/login` が `/` へ送り返して往復する。

```
/       → middleware が「未ログイン」と判定 → /login へ
/login  → getServerSession が「ログイン済み」と判定 → / へ
/       → …以降無限に往復
```

この状態では**画面が一切描画されず、アプリのログもエラー画面も出ない**。調査手段は外形的なもの（`curl` でのリダイレクト追跡、DevTools のクッキー確認）に限られ、実際それらを尽くしても原因に辿り着けなかった。

問題は「食い違いが起きたこと」だけではない。**食い違いが起きうる構造**と、**起きたときに何も観測できないこと**の 2 点である。

## 検討した代替案

- **案A（採用）：判定を middleware の `getToken` 1 か所に閉じる**
  - `/login` を middleware の除外対象から外し、middleware 内で「未ログインなら通す / ログイン済みなら `/` へ戻す」を分岐する
  - `login/page.tsx` から `getServerSession` を削除する
  - 判定が 1 つしか存在しないため、食い違いが原理的に発生しない
- **案B：`/login` 側にループ防止のガードを足す（`callbackUrl` が付いていたら `/` へ戻さない）**
  - 往復は止まるが、**判定の食い違いそのものは残る**。利用者は「ログインしても毎回ログイン画面に戻る」状態になり、壊れていることに変わりはない
  - しかも症状が見えにくくなるぶん、原因追跡はむしろ難しくなる。不採用
- **案C：`/login` の `getServerSession` を単に削除する（middleware に戻す処理を足さない）**
  - ループは止まり、実装も最小。ただし `src/components/layout/header.tsx` はログイン画面でヘッダーを隠すため、ログイン済みの利用者が `/login` を開くと**ナビゲーションの無い画面に取り残される**。不採用
- **案D：現状維持（環境変数の設定ミスとして扱う）**
  - 実際には `NEXTAUTH_URL` も Google のリダイレクト URI も正しく設定されていた。設定ミスではなかったため、同じ事象が再発する。不採用

## Decision

**ログイン済みかどうかの判定は `src/middleware.ts` の `getToken` だけが行う。画面側（サーバーコンポーネント）に `getServerSession` などの 2 つ目の判定を置かない。**

- `/login` は middleware の除外対象にしない。middleware が `getToken` の結果 1 つで次を決める
  - トークンあり ＋ `/login` → `/` へリダイレクト（従来 `login/page.tsx` にあった利便機能）
  - トークンなし ＋ `/login` → 通す
  - それ以外は ADR 0011 の判断どおり（画面はログイン画面へ、`/api/*` は 401 JSON）
- middleware の除外は `api/auth` / `api/batch` / `_next` / `favicon.ico` のみ
- `getToken` が `null` を返した場合、`raw: true` で取り直してクッキーの有無を確かめ、**クッキーは届いているのに復号だけ失敗している場合はログに出す**

### 理由

- 判定が 1 つなら、2 つの判定が食い違うという事象自体が存在しない。ループは構造的に発生しない
- `next-auth` v4 では middleware（Edge）から `getServerSession` を呼べず、サーバーコンポーネントから `getToken` を呼ぶのも綺麗ではない。**2 系統を統合するなら middleware 側に寄せるしかない**
- `getToken` はクッキーが無い場合も復号に失敗した場合も等しく `null` を返す（実装が `catch { return null }` で握りつぶす）。この区別が付かないことが「原因を追えない」ことの中核だったため、ログで区別できるようにする

## 決定していないこと

- **ログの送り先**。`console.error` で Vercel のランタイムログに出すだけとし、外部の監視サービスへは送らない。単一ユーザー運用で、障害に気づくのは所有者本人であるため
- **ログイン試行の記録**。誰がいつログインしたかは記録しない（ADR 0011 の「監査ログを持たない」判断を引き継ぐ）
- **クライアントコンポーネントでの `useSession` の扱い**。`src/components/layout/header.tsx` はログイン中のメールアドレス表示とログアウト操作に `useSession` を使っている。これは**アクセス可否を決める判定ではなく表示のため**なので、本 ADR の対象外とする

## Consequences

- `/login` が middleware を通るようになる。全リクエストで `getToken` が走るのは従来どおりで、負荷の増加は `/login` の分だけ
- `login/page.tsx` からセッション読み取りが無くなり、**静的ページになる**（ビルド出力で `○ /login`）
- 新しい画面でログイン状態に応じた出し分けをしたくなったとき、**サーバーコンポーネントで `getServerSession` を呼んではいけない**。必要なら middleware 側で分岐するか、クライアントの `useSession`（表示用途に限る）を使う
- 認証で詰まったときの調査は、まず Vercel のランタイムログを見る。手順は [`docs/deployment.md`](../deployment.md) の「ログインできない場合」

### プレモーテム（この決定が誤っていた場合）

- middleware は Edge ランタイムで動くため、Node 固有の API を必要とする判定（DB 参照など）は書けない。マルチユーザー化して「ユーザーごとに閲覧可否を変える」要求が出たとき、判定を middleware に閉じたままでは実装できず、本 ADR を覆すことになる
- middleware が全リクエストを通るため、ここでの例外はアプリ全体を落とす。`getToken` を 2 回呼ぶ（`raw` の取り直し）ぶん、失敗点がわずかに増えている
- ログイン済みで `/login` を開いたときのリダイレクトが middleware に移ったため、この挙動の変更は middleware の修正を伴う。画面側だけを見ている人には所在が分かりにくい

## 見直しトリガー

- マルチユーザー化し、ユーザーごとに画面の出し分けが必要になったとき（Edge で判定しきれなくなる）
- `next-auth` を v5（Auth.js）へ上げたとき。`auth()` が Edge / Node の両方で使えるため、統合の仕方を見直せる
- middleware で判定できない認可要件（ロール・権限）が出たとき
- 「セッションクッキーは届いているが復号できませんでした」のログが実際に出たとき（原因が特定でき次第、対処を ADR に反映する）
