# 時間と日付の扱い

このアプリで日付がどう決まり、どう保存され、どう表示されるかをまとめる。

---

## 1. 「瞬間」と「暦日」は別物

このアプリの日時には、性質の違う 2 種類がある。

| | 瞬間（instant） | 暦日（calendar day） |
| --- | --- | --- |
| 意味 | 世界のどこでも同じ 1 点 | カレンダー上のラベル |
| 例 | 「価格を取得した時刻」 | 「東証の 8/21 の営業日」 |
| 時刻を持つか | 持つ | **持たない** |
| 見る場所で変わるか | 表示が変わる（NY なら 9 時間前） | **変わらない**（8/21 は 8/21） |
| 保存と表示 | 世界標準時で保存し、表示時に変換する | 日付をそのまま保存し、**変換しない** |

### どのカラムがどちらか

**型が意味と一致している。** 暦日のカラムは `DATE`、瞬間のカラムは `DATETIME`。

| カラム | 種類 | DB の型 |
| --- | --- | --- |
| `DailyPrice.priceDate` | 暦日 | `DATE` |
| `ExchangeRate.rateDate` | 暦日 | `DATE` |
| `Transaction.transactionDate` | 暦日 | `DATE` |
| `DividendHistory.paymentDate` | 暦日 | `DATE` |
| `Stock.firstPurchaseDate` / `purchaseDate` / `saleDate` | 暦日 | `DATE` |
| `PriceHistory.recordedAt` | 瞬間 | `DATETIME` |
| `Stock.lastPriceUpdate` | 瞬間 | `DATETIME` |
| `createdAt` / `updatedAt` | 瞬間 | `DATETIME` |

`DATE` 型は時刻を持てないため、**書き込み経路が違っても時刻が混在しない**。Prisma は `DATE` 列を読むとき世界標準時 0 時の `Date` を返すので、そのまま暦日キーとして扱える。

---

## 2. 暦日キー

暦日は **暦日キー** という値で扱う。実装は [`src/lib/date-key.ts`](../../src/lib/date-key.ts)。

暦日キーは「**日本時間の暦日**」を「**世界標準時 0 時の `Date`**」で表す。

| 関数 | 役割 |
| --- | --- |
| `toDateKey(instant)` | 時刻 → その時刻が属する暦日 |
| `formatDateKey(date)` | 暦日 → `"2026-08-21"` |
| `dateKeyOf(y, m, d)` | 年月日 → 暦日 |
| `dateKeyParts(key)` | 暦日 → 年月日 |
| `addDays(key, n)` | 暦日を n 日進める |
| `startOfWeekKey(key)` | 暦日 → その週の月曜（週単位でまとめるときのキー） |
| `jstMinutesOfDay(instant)` | 時刻 → 日本時間 0 時からの経過分（前場・後場の判定用） |

### なぜ世界標準時 0 時で持つのか

Prisma が `DATE` 列へ書くとき、渡された `Date` の**世界標準時側の日付**を取るため。書きたい日付を世界標準時側に置いておけば、保存した日付と読み戻した日付が一致する。

```
渡した値                           MySQL の DATE 列に入る値
2026-01-04T15:00:00Z（日本時間 1/5 0 時）  →  2026-01-04   ← 1 日戻る
2026-01-05T00:00:00Z（世界標準時 1/5 0 時）  →  2026-01-05
```

> Prisma の内部実装は確認していない。実際に書き込んで観測した挙動である。

### なぜ日本時間で日を決めるのか

`DailyPrice.priceDate` が表すのは東証の営業日で、東証の営業日は日本時間で区切られるため。

ただし**現在の対応市場では、日本時間で区切っても世界標準時で区切っても結果は同じ**である。

| 市場 | 立会時間 | 世界標準時では |
| --- | --- | --- |
| 東証 | 9:00〜15:00 JST | 0:00〜6:00（同じ日） |
| 米国 | 9:30〜16:00 ET | 13:30〜20:00（同じ日） |

日本時間に固定しているのは、同じ `toDateKey` を「今日・今月・今年」の判定でも使っており、**そちらは日本時間で区切らないと日本の朝 0〜9 時に「昨日」「先月」と表示されてしまう**ため。区切りは 1 つに揃える必要がある。

### 実行環境のタイムゾーンに依存しない

`getTime()`（絶対値）と定数演算しか使っていないため。

```js
export function toDateKey(instant: Date): Date {
  const jst = instant.getTime() + JST_OFFSET_MS   // 絶対値 + 定数
  return new Date(Math.floor(jst / DAY_MS) * DAY_MS)
}
```

サーバーのタイムゾーンを何に変えても結果は同じ（テストは UTC+14 から UTC-7 まで通ることを確認済み）。

**サーバーのタイムゾーンは揃えられない前提で考える。** 開発機は各自の設定、Vercel の関数は UTC で、`TZ` は Vercel の[予約環境変数](https://vercel.com/docs/environment-variables/reserved-environment-variables)のため変更できない。日付の扱いは実行環境に依存しない書き方にする必要がある。

## 3. 資産推移グラフには 2 つの局面がある

| | cron 実行（書き込み） | 画面表示（読み取り） |
| --- | --- | --- |
| いつ | 1 日 1 回・日本時間 08 時台 | 画面を開くたび |
| すること | Yahoo から終値を取り、`DailyPrice` に**行を追加**する | 起点日から今日まで 1 日ずつ**点を組み立てる** |
| 保存するか | する（既存の日は上書きしない） | **しない**。毎回その場で計算する |
| 実装 | [`backfillDailyPrices`](../../src/lib/daily-price.ts) | [`computeTimeline`](../../src/lib/portfolio-timeline.ts) |

**画面を開くこと自体では、データは増えない。** 同じ日に何回開いても同じグラフになる。

```
8/21 08:30  【cron】  8/20 までの株価を取り込む
8/21 10:00  【画面】  8/20 まで確定 / 8/21 は仮（8/20 の株価）
8/21 15:00  東証 大引け → 8/21 の日本株の株価が決まる（まだ取り込んでいない）
8/21 16:00  【画面】  変わらない
8/22 05:00  NY 引け     → 8/21 の米国株の株価が決まる（まだ取り込んでいない）
8/22 08:30  【cron】  8/21 の株価を取り込む   ★ここで 8/21 が確定
8/22 09:00  【画面】  8/21 まで確定 / 8/22 は仮（8/21 の株価）
```

- **グラフの右端（今日）は常に仮**。その日の行がまだ無いので、前日の株価をそのまま引き継ぐ（forward-fill）
- 株価は前日と同じでも、**保有株数はその日の取引を反映する**（評価額 = 保有株数 × 終値）
- **確定した過去の点は、以後変わらない**（既存の行を上書きしないため）

今日の行が作れないのは、その日の終値が両市場で出そろうのが翌朝だから。東証の大引けが当日 15:00、NY の引けが翌日 05:00（いずれも日本時間）で、cron はその後に走る。

## 4. グラフの 1 点が表す時点

1 点は「**その営業日の市場がすべて閉じた時点**」の評価額を表す。

| 構成要素 | 値が確定する時刻（日本時間） |
| --- | --- |
| 国内株の終値 | 8/21 15:00 |
| 米国株の終値 | **8/22 05:00** |
| USD/JPY レート | 8/21 の日次レート |
| 保有株数 | 8/21 までの取引を反映 |

**1 つの点の中に約 14 時間の開きがある。**「8/21 の 15:00 に全部売ったらいくらか」ではない。

営業日カレンダーが日米で異なる点は forward-fill で吸収している。

- 日本の祝日：東証は休場、NY は稼働 → 国内株だけ前日値
- 米国の祝日：その逆

forward-fill は**銘柄ごとに独立**して動くため、片方の市場だけ前日値になる状態を表現できる。

## 5. タイムゾーンを変えたときの影響

| | サーバーの TZ を変える | ブラウザ（PC）の TZ を変える |
| --- | --- | --- |
| 日次終値の保存日 | 影響なし | 関係なし |
| 資産推移グラフ | 影響なし | 影響なし（API が `"2026-08-21"` という文字列で返すため） |
| 前場・後場の判定 | 影響なし | 関係なし |
| 取引一覧・配当一覧の日付表示 | 影響なし | 影響なし |
| 価格履歴の週次・月次グラフ | 影響なし | 関係なし |

日付を表示する [`formatDate` / `formatDateTime`](../../src/lib/utils.ts) は、`Intl.DateTimeFormat` に `timeZone: 'Asia/Tokyo'` を指定している。指定を省略すると実行環境のタイムゾーンが使われ、サーバーで描くかブラウザで描くか、どの国で開くかによって日付が変わってしまう。

## 6. コードを書くときのルール

- **`new Date(y, m, d)` を使わない。** これは「実行しているマシンのタイムゾーンでの 0 時」という意味になり、環境で結果が変わる。暦日を作るときは `dateKeyOf(y, m, d)` を使う
- **`DATE` 列へ書く値は `toDateKey` を通す。** 画面から受け取った `"2026-06-30"` のような文字列を `new Date()` に渡しただけでも今は正しく入るが、時刻付きの値が来たときに日本時間の暦日にならない
- **`getFullYear()` / `getMonth()` / `getDate()` / `getHours()` を使わない。** これらはローカルのタイムゾーンで読む。暦日から年月日を取り出すときは `dateKeyParts(key)` を使う
- **日付を扱うテストは `dateKeyOf` か `Z` 付き ISO 文字列で組み立てる。** ローカル暦日で書くと、テストが実行環境のタイムゾーンに依存する
- 「今日・今月・今年」の境目、東証の立会時間の判定も日本時間で行う

## 7. 未対応

### 取引所ごとの営業日カレンダー未対応

東証と NY の終値を同じ暦日に載せている。

- **影響**：1 点の中に約 14 時間の開きが生じる（[4 章](#4-グラフの-1-点が表す時点)）。日米の休場日の差は forward-fill で吸収している
- **未対応の理由**：対応市場が 2 つで、どちらの立会時間も暦日をまたがないため、現状の作りで成立しているため
